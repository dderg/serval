# Smooth Shapers Port (from bleeding-edge-v2)

**Date:** 2026-04-20
**Branch:** `smooth-shapers` (cut from `blend-arc`)
**Worktree:** `~/Developer/kalico-smooth-shapers`

## Goal

Bring Dmitry Butyugin's **smooth input shapers** from `upstream/bleeding-edge-v2` into
this Kalico fork, together with the non-linear pressure advance / extruder refactor
chain it depends on. Adapt the `target_smoothing` runtime cap (blend-arc feature) so
it remains correct when a smooth shaper is configured, not just for impulse shapers.

## Background

### Smooth shapers vs impulse shapers

The current shaper implementation (main / blend-arc / upstream stable) models input
shaping as a **discrete impulse train** — finite dirac impulses convolved with the
toolpath. Each axis replays a small set of impulses `(A_i, t_i)` at the chelper
level (`kin_shaper.c`).

Smooth shapers replace this with a **continuous support function** `S(t)` whose
integral equals one over a finite window `2·t_sm`. The convolution is evaluated
analytically (via antiderivatives in `integrate.c`) rather than by summing impulses.

Advantages claimed upstream:

- Lower velocity-envelope ripple over the same vibration suppression
- Cleaner extruder sync (PA smoothing couples with shaper smoothing continuously)
- Better numerical stability at small step intervals

### blend-arc's `target_smoothing` knob (current fork)

`blend-arc` already introduces a user-tunable `target_smoothing` value that caps
the runtime accel so the *effective shaper smoothing distance* stays under a budget.
That cap was derived against an **impulse-shaper** velocity envelope. When a smooth
shaper is configured, the envelope has a different shape (continuous support
instead of delta-train) and the current cap formula is no longer correct.

## Scope

### In scope

1. Port the PA / extruder refactor chain from `upstream/bleeding-edge-v2`:
   - X/Y/Z extruder motion split
   - Time-offset between extruder and kinematic moves
   - Explicit PA velocity term + numerical-stability fix
   - Non-linear pressure advance
   - Extruder sync with input shaping
   - `linear_offset` → `nonlinear_offset` rename
2. Port the smooth-shaper core:
   - Custom input shaper support (pre-req for smooth path)
   - Smooth input shaper kinematics (`kin_shaper.c`, `integrate.c` antiderivatives,
     header / chelper wiring)
   - Custom smoothers for the extruder (`aad71be9`, `7ac2c445`)
   - `shaper_defs.py INPUT_SMOOTHERS` table containing **all six** smooth variants:
     `smooth_zv`, `smooth_mzv`, `smooth_ei`, `smooth_2hump_ei`, `smooth_zvd_ei`,
     `smooth_si`
3. Port `shaper_calibrate.py` and scripts support for smoothers
4. **Prune** the impulse-shaper set on this branch down to `zv` and `mzv` only.
   Remove every other impulse shaper (`ei`, `2hump_ei`, `3hump_ei`, `zvd`, `si`, etc.)
   from `shaper_defs.INPUT_SHAPERS`, `shaper_calibrate.AUTOTUNE_SHAPERS`, and any
   scripts / docs that reference them.
5. **Adapt `target_smoothing`** so it picks the correct cap formula based on the
   configured shaper family (impulse vs smooth) on that axis. Math to be derived
   and numerically verified by a research subagent.

### Out of scope (explicitly deferred)

- BE-v2's unrelated work that happens to touch the same files:
  - `motan` extended-format queued-step reporting
  - New high-precision stepping protocol
  - chelper `O3 / NEON / native` optimization flags
  - `*EI` impulse-shaper redefinition (we're removing those impulse shapers)
- Upstreaming this work (no feature flags / compat shims; this branch replaces
  behavior cleanly, per fork-as-gate policy).

## Approach

### Isolation

Work happens in a dedicated git worktree (`~/Developer/kalico-smooth-shapers`) on
branch `smooth-shapers` cut from `blend-arc`. Keeps `blend-arc` untouched while the
port is in flight; worktree is throwaway if the approach is wrong.

### Cherry-pick (not merge)

The ~27 BE-v2 commits that touch shaper / extruder / integrate / trapq files are
cherry-picked individually in topological order. Merging BE-v2 wholesale pulls in
stepper-protocol, motan, and other unrelated work whose blast radius is much larger
than the shaper port and harder to separate later.

**Exact ordered pick list and per-commit skip/adapt notes are produced by the
implementation plan, not this spec.** The plan will be generated by
`writing-plans` after this spec is approved, with a git-archaeology subagent
resolving inter-commit dependencies (e.g., whether `cad447cc extruder sync with
input shaping` requires any piece of the skipped stepper/motan commits).

**Commits to skip (known):**
- `dc2c4d98` motan extended-format queued-step reporting
- `9c49716e` high-precision stepping protocol
- `f7a57f05` chelper O3/NEON/native flags (performance, unrelated)
- `36255dec` updated impulse-EI shaper defs (we're dropping impulse EI)

**Commits to skip or adapt TBD:** the `*EI`-smoother and extruder-smoother commits
may need minor pruning to match our shaper set. Per-axis or per-shaper pruning
decisions happen at pick-time.

### Shaper-family-aware `target_smoothing`

The current impulse-era cap derivation lives in `input_shaper.py`. After the port,
each axis configuration knows whether its shaper is impulse-family or
smooth-family (the Python class differs). The cap formula will branch on that.

**The derivation of the smooth-shaper cap is delegated to a research subagent.**
The subagent produces:

1. Closed-form (or tight numerical bound) for the smooth-shaper velocity-envelope
   area / effective smoothing distance under a support-function basis.
2. Numerical cross-check against the current impulse formula at a limiting case
   (impulse = limit of a narrow support function). These must agree as the
   support width → 0.
3. The smooth-shaper analogue of the mainline-SCV floor check (`5743ed91`): the
   cap should not make the planner slower than a hypothetical mainline-SCV with
   no smooth-shaper cap, else disable itself for that corner.
4. A recommendation for the formula's form in `input_shaper.py`.

Input to this spec: design goal of "cap runtime accel so post-shaper smoothing
distance ≤ `target_smoothing`". Output stays in scope. Subagent does NOT
decide product goals, only math.

## Design decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Kept impulse shapers | `zv`, `mzv` only | User ruled: others not in use; reduces calibrate/plot clutter. |
| Kept smooth shapers | All six (`smooth_zv`, `smooth_mzv`, `smooth_ei`, `smooth_2hump_ei`, `smooth_zvd_ei`, `smooth_si`) | Testing unknown; keep full set from BE-v2 while we explore. |
| Port method | Cherry-pick chain | Smallest blast radius; skips unrelated BE-v2 work cleanly. |
| Isolation | Git worktree | Reversible if port dead-ends. |
| `target_smoothing` | Dispatch on shaper family per axis | Correct by construction; no flags, no fallback mode. |
| Calibrate exclude-list | Deferred | Not blocking; user explicitly scoped out. |

## Verification strategy

### Static checks

- `klippy/chelper/__init__.py` builds (`c_helper.so` rebuilds without warnings).
- `python -m compileall klippy/` clean.
- Lint / type checks on changed files.

### Python-level tests

- Existing host-simulator regression config under `test/configs/` runs with
  `zv`, `mzv`, `smooth_zv`, `smooth_mzv` each configured on a toy axis. No
  exception, no flood of warnings, deterministic step-queue output.
- `SHAPER_CALIBRATE` dry-run on recorded resonance data (subagent-provided fixture
  if needed) — candidate list reflects new shaper roster.

### Numerical check on `target_smoothing`

- Before-rewrite baseline: measure effective smoothing distance on a canned path
  under `target_smoothing = 0.12 mm`, impulse `mzv`, current formula.
- After-rewrite: repeat with the new family-aware formula, impulse `mzv`.
  Expected outcome: **identical** smoothing distance (impulse branch is
  unchanged in effect, just refactored).
- New case: same path, `smooth_mzv`, `target_smoothing = 0.12 mm`. Smoothing
  distance stays ≤ budget; feed to subagent for numerical cross-check.
