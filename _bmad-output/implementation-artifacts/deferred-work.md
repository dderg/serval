## From spec-motion-2-execution-lowering (review 2026-06-18)

- **Small-σ Fresnel precision cliff.** `clothoid_offset`'s σ=0 closed form fires only at exactly `sigma == 0.0`; for tiny nonzero σ the completion-of-square produces large Fresnel arguments whose differenced ~0.5-magnitude values cancel (error grows to ~3e-9 at σ=1e-9). Sub-physical (picometer-scale) and degenerate-arc-like, so not patched now. Add a tolerance-band fallback to the arc/line limit if the fitter ever emits near-arc clothoids.
- **`LoweredSample.followers` drops `axis_index`.** Follower samples are a positional `Vec<f64>` of `ratio·s` in `seg.followers` order; `FollowerDemand.axis_index` is not carried. Fine for observability (zip with `seg.followers`), but revisit the struct shape when a real follower consumer (front-end, step 3+) needs the axis mapping.

- **Signed-curvature convention (step-2 heading).** `Arc::kappa` returns `+1/radius` regardless of sweep sign, while `Clothoid::kappa` is signed (`κ₀ + σs`). The velocity cap consumes `|κ|` via `kappa_peak`, so step 1 is correct. If a downstream consumer needs signed curvature to distinguish turn direction (heading integration), settle the sign convention when that consumer lands.

## From spec-motion-3-frontend-gcode (review 2026-06-18)

- **Tiny-segment follower-ratio blow-up (extruder velocity spike).** A near-zero-length arc/line (`arc_length`/`spatial_distance` just above the `1e-9` displacement epsilon) carrying a real extrusion delta produces a follower `ratio = e_delta / length` of thousands — a micron-scale path commanding mm-scale extruder motion. The `1e-9` epsilon gates extrusion and spatial displacement independently but nothing bounds the resulting ratio. Sub-physical for representative slicer output and identical in shape to the existing `motion-engine::classify_and_build`, so not patched in the frontend. The principled fix is an **extruder-velocity / volumetric-flow cap in the velocity planner** (step 5+, see architecture "Volumetric-flow cap" / PA-augmented transient) — geometry has no velocity limit to check against. Revisit when that cap lands.

## Deferred from: code review of spec-motion-8-chain-fit (2026-06-18)

- **Greedy `detect_runs` never backtracks the run end.** On a `reconstruct` abandonment for the maximal candidate `[i..=end]`, the scanner advances the start (`i += 1`) and regrows, so it only ever tries co-circular *suffixes*, never the shorter *prefix* `[i..=end-1]`. A single non-co-circular trailing facet therefore prevents reconstruction of an entire long, otherwise-co-circular arc (it falls back to the per-corner sawtooth) — a throughput regression on "mostly clean with one blemish" runs. Uniform arcs (the dominant #4228 case) reconstruct in one shot, so V1 ships without backtracking; add an inner shrink-the-end retry when a sub-maximal reconstruction would beat the per-corner fallback. (`fitter/chain.rs::detect_runs`)
- **No observability when a detected run abandons reconstruction.** When a run passes detection (same-turn, coplanar, ≥`min_run_junctions`) but `reconstruct` returns `None` (residual > `cocircular_tol`, seam miss, budget/shift failure, or vertex-tube miss), the span silently degrades to the per-corner path with no counter or reason recorded in `FitReport`. A single anomalous facet's limits (tiny δ ⇒ `l_t` underflow) nukes a long run with no diagnostic. Add an abandoned-chain counter / reason enum to `FitReport` for tuning visibility. (`fitter/chain.rs`)
## Deferred from: code review of spec-motion-9-profile-lowering (2026-06-18)

- **`lower_profile` sample count is unbounded for absurdly-tiny-positive velocities.** The per-interval guard rejects `v_sum <= 0` but admits arbitrarily small positive velocities (e.g. both endpoints `~1e-12`), so the interval duration `2·Δs/v_sum` and hence the global fixed-rate sample count `n` can grow enormous-but-finite — below the `count + 1 >= usize::MAX` addressable-range guard, so `Vec::with_capacity(n+1)` OOM-aborts rather than returning a clean `InvalidLowering`. Not reachable from the real `plan_velocity` producer (its velocity epsilon is `1e-9`, and the forward/backward reach from any rest anchor under positive accel is strictly bounded below), and identical in shape to the pre-existing `lower_constant_speed` count guard (`path/lowering.rs`). The principled fix is a deliberate max-samples-per-trajectory cap (or a minimum-traversal-velocity floor) returning `InvalidLowering`, applied consistently to both lowering entry points — a value to pin, not guess. (`rust/geometry/src/execution.rs::lower_profile`)

- **`solve3` tests hard-singularity (`|det| < 1e-18`), not conditioning.** The incircle normal-equations solve guards only an exactly-singular matrix; a near-degenerate (near-straight, huge-radius) run yields a finite but ill-conditioned `(O, ρ)`. In practice the downstream `cocircular_tol` residual gate, the `rho > BUDGET_EPS` check, and the `delta_sweep > ANGLE_EPS` gate backstop it (a near-straight run has `theta_run ≈ 0 ⇒ delta_sweep ≤ 0 ⇒ abandon`), so no incorrect output reaches the planner — but the intended singular-matrix guard is not doing the conditioning job. Switch to a condition-number / normalized-pivot test if a near-straight faceted run ever needs explicit rejection. (`fitter/chain.rs::solve3`)

## From spec-motion-14 T2 (found 2026-06-21)

- **Jerk-aware peak estimation in the forward/backward sweep.** The base velocity sweep (`velocity.rs` / `disk.rs` forward/backward branches) marks a move as reaching `flat_ceiling` using disk/scurve reachability that ignores the jerk-down distance needed to *land* on the ceiling at `a=0`. For a straight shorter than `~2×` the jerk-limited accel distance, the reported peak (`v_max`) is therefore **not jerk-feasible** — the move's true peak is below `v_max`, and the Motion-14 entry/exit roll-offs overlap. Motion-14 detects this overlap and falls back to the base profile (keeping its cruise-touch step) instead of emitting interleaved arcs (`disk.rs::reconstruct_flat`, guarded by `cruise_onset.rs::short_overlap_move_falls_back_to_base_without_garbage`). Only reachable at low jerk — realistic configs (Neptune `j=1e6`) have sub-millimetre roll-offs and never overlap — so low priority. Proper fix: make the sweep's peak estimate account for the jerk-limited up+down ramp so the reported peak is feasible (then a short move peaks below `v_max` and is handled by the existing sign-flip apex bridge, no special case). See spec-motion-14 R4.

## From spec-arc-fit-config-section (review 2026-06-19)

Pre-existing / hardening items surfaced while adding the opt-in `[arc_fit]` gates; not caused by that change:

- **Leading-collinear run never reconstructs.** `fitter/chain.rs::reconstruct` anchors its plane on `turn_normal(t0, lines[1])`; if a run begins with a collinear pair (`grow_run` advances past a `theta<=theta_min` first junction), those headings are parallel → `turn_normal` returns `None` → the whole run is dropped to per-corner. - **O(n²) re-growth on gate-split runs.** When `grow_run` breaks on the new length/angle gate below `min_run_junctions`, `detect_runs` falls to `i += 1` and re-grows over largely the same facets. Pathological faceting can make this quadratic. Consider advancing `i` past the inspected span on a sub-threshold break.
- **`ChainFitConfig::with_arc_fit` / `ArcFitConfig` are not self-validating.** Production validates knobs at the FFI boundary (`bridge.rs` + klippy `getfloat`), and the rest of the config types follow the same validate-at-boundary pattern, so internal callers are trusted. The test helper deliberately passes `f64::INFINITY`/`PI` as an "ungated" sentinel. If a future non-boundary Rust caller appears, add a `try_*` constructor rather than validating in `with_arc_fit` (which would break the sentinel idiom).
- **No automated test for the bad-param config error.** `max_angle_deg`/`facet_length_mm` non-positive (and now `max_angle_deg >= 180`) are rejected by klippy `getfloat(above=0.0, below=180.0)` and a bridge `PyValueError` backstop — verified by inspection, but no regression test exercises either error path. ## From spec-pressure-advance-port (review 2026-06-22)

Real items surfaced by the 3-reviewer pass on the PA implementation; none are caused-and-trivially-fixable within this story (all CAPs/acceptance pass):

## Continuity commit — follow-ups (from continuity-commit work, 2026-06-22)

- **Redundant re-lowering of the held-back look-ahead tail.** `StreamState::commit` re-fits, re-plans, and re-lowers the *entire* uncommitted buffer on every call, but the trailing `keep_secs` window is held back (not committed) and then re-lowered identically on the next commit. With per-move committing in `run_loop`, that tail is lowered once per incoming move. Cost is O(tail) per move — bounded and cheap for representative slicer density (the tail is a handful of moves), but genuinely wasteful and the dominant per-move cost for very dense streams. Principled fix: cache the lowered/planned tail and only re-lower the dirty suffix (the new move + the δ-reach of the previous tail end), or fit incrementally. Pin the cache-invalidation boundary to the fitter's δ-locality reach. (`rust/motion-engine/src/stream.rs`, `stream_planner.rs` move handler)
- **Continuity commit across arc-run reconstructions is unverified by test.** The head-trim logic (`blend_consumed_head` + `trim_front_to_seam`) is derived to also cover arc runs (the run-end down-clothoid shares its source line with the run-end move body, so head-trim triggers and the run-end move is trimmed to the seam), but `arc_fit` is off by default and no test exercises a mid-run continuity commit. Add coverage when arc-fit is enabled in production, asserting position/extrusion continuity across a commit that lands at a reconstructed-arc exit.

## 2026-06-22 — from submission-aware backpressure review (spec-submission-aware-backpressure)

- **`queued_motion_secs` reads two atomics without a consistent snapshot.** `bridge.rs` computes `(last_move_time() - est) + uncommitted_intake_secs()` as two separate Acquire loads of two independently-updated atomics (`last_move_time_bits` and the tally), both written by the planner thread but not under one lock. A read can straddle a commit and momentarily mix a new frontier with an old tally (double-count) or vice-versa (under-count). Bounded by one batch, self-correcting on the next ~10 ms `_check_pause` tick, so the gate impact is negligible — but a future maintainer relying on this signal for anything sharper should publish (frontier, tally) atomically together (e.g. a seqlock or a single packed value). (`rust/motion-engine/src/bridge.rs` `queued_motion_secs`)
- **Stale `last_move_time` is exposed across `Reset`/`StreamOpen` by the new signal.** On reset/stream-open `t_committed` and the tally go to 0 but `last_move_time_bits` keeps the pre-reset frontier until the next dispatch re-anchors it. `queued_motion_secs` (and the `stats()` `buffer_time` it now feeds, plus `get_status`) can therefore read `(stale_frontier - est)` in that window. In practice est tracks the MCU which has played out to ~the old frontier by the time a new stream opens, so the difference is ~0 and any spurious pause self-heals on the first post-reset commit — but nothing enforces that ordering. Consider zeroing/re-anchoring `last_move_time_bits` on the reset paths (the tally already resets there). Interacts with the second-run-reanchor logic — verify against that spec before changing. (`rust/motion-engine/src/stream_planner.rs` reset paths)
- **A single move whose nominal exceeds `DRAIN_TIMEOUT` (60 s) false-trips the gate.** One very long, very slow move can make `queued_motion_secs > buffer_time_high` and not drain within `DRAIN_TIMEOUT`, raising the "MCU not retiring moves" `command_error` even though nothing is stalled (the move is simply playing out). Exotic (a >60 s single move), so deferred; if it ever surfaces, exempt single-move backlogs or scale the deadline by the lead move's nominal. (`klippy/motion.py` `_check_pause`)
- **`ChannelFull` host handling + the gate's blindness to in-channel depth.** The bounded planner channel (`INPUT_CHANNEL_CAP = 8192`) raises `ChannelFull` → `PyRuntimeError` → printer shutdown when full. The gate counts only moves the planner has *intaken* (the tally), not moves still queued in the channel, so a CPU-bound planner that falls behind a fast feeder can fill the channel while the gate stays open — tripping the fail-loud backstop on a throughput situation rather than a true MCU stall. This is consistent with the project's "fail loud if the host can't keep up" philosophy, but: (a) there is no host-side test that `submit_move` raising `ChannelFull` surfaces cleanly, and (b) if benches hit it on dense short-move bursts, revisit (raise CAP, or fold channel depth into the signal). (`rust/motion-engine/src/{bridge,stream_planner}.rs`, `klippy/motion.py`)

## 2026-06-26 — deferred from spec-causal-unified-fitter (scope split at planning)

- **Overlap fallback ladder for clustered / sharp corners (the hard sub-problem).** The causal-unified-fitter spec (`spec-causal-unified-fitter.md`) was split to land the cutover first; this is the deferred second deliverable. Build the deterministic fallback ladder for when flanking legs are shorter than the combined runway L≈√(24Rδ): (1) arc-aware decimation (Gribov, not plain Douglas–Peucker — shares ONE tolerance budget with the fillet, no decimate-then-fillet 2δ double-count); (2) full fillet L=√(24Rδ); (3) asymmetric shrink L_in≠L_out so each side uses its own runway; (4) merge — fit ONE biclothoid across a cluster when even a segment-scale biclothoid won't fit; (5) terminal rung is a tiny high-κ biclothoid, **never** a drop to G1 / curvature step. Merges must **not** cross an inflection (curvature sign change) — split clusters at inflections, merge only within monotone-turning runs [OV#3]. Note: the isolated-tip clamp (κ_peak=θ/L, δ shrinks as L shrinks) lands in the cutover spec and always succeeds for an *isolated* corner — the merge rung is only for corner *clustering* [OV#5]. Target regime/test: the real corner cluster + ~0.2 mm sharp tip in `snapshots/cases/arc_fit/fillet.gcode`. Lives in `rust/geometry/src/fitter/overlap.rs` + `overlap/tests.rs` on top of the (by-then-stable) causal driver. Per the brainstorming this is "where the actual novel work is" (PA#5, OV#2).
- **Adjacent arc spans get no transition → κ-step under motion (measured during the cutover).** Surfaced by the new `rust/geometry/tests/heart_comparison.rs` jittered-dense-arc stress case (PA#2's pathological sub-mm noisy slicer input). On that input the span detectors fragment one curve into multiple spans; the driver eases an arc only into *unoccupied* straight neighbours (`chain_runs` head/tail `!occupied` check, inherited from the old `attach_boundary_blends`), so two ADJACENT arc spans meet with no clothoid between them — a real curvature step under motion (PositionGreedy: `A[0.333] A[0.343] A[0.502]`, κ-jump 0.159), not the harmless at-rest arc↔line step. KappaSignal instead splits with bare lines (`A L A L A L`, 3 mid-curve stops). This is PRE-EXISTING (the old two-stage fitter had the same `!occupied` easing restriction) and is preserved faithfully by the cutover; real slicer arcs (the `circle.gcode` baseline) are clean enough to fit as one span so it does not bite them. The overlap ladder must (a) MERGE adjacent same-sign arc spans into one within tolerance, or (b) insert an arc→clothoid→arc transition between differing-κ adjacent spans — never leave adjacent bare arcs. `heart_comparison` is the ready-made measurement for this regime.
- **Arc-easing leaves sub-tube C0 gaps (up to ~8µm) on some gentle-curve configs (found by `fit_proptest`).** The reused `joint_refit`/`build_spiral`/`choose_circle` kernels place the eased circle and its transition spiral semi-independently, so on certain arc-easing geometries consecutive emitted segments do not meet bit-exactly — gaps range from sub-µm to ~8µm. Clean canonical easings (the deterministic `causal/tests.rs`) are C0 to 1e-6; this only shows on randomized gentle 2-turn curves. ## 2026-06-26 — from adversarial review of the causal-unified-fitter cutover

- **`occupied[]` built from claimed spans, not accepted runs; no shorter-prefix retry.** `causal::chain_runs` marks a heart's claimed span `occupied` before `kernels::reconstruct` runs; if reconstruct returns `None` the span is dropped (`continue`) but its slots stay occupied, so an adjacent accepted run won't ease into them — and unlike the old `detect_runs`, there is no `span_start+1` retry of a shorter cocircular prefix. Only reachable when a span passes `cocircular` but fails `reconstruct` (near-zero-sweep degenerate); does not affect the 10/10-exact snapshot cases. Fix when tightening: reconstruct first, then mark occupied from accepted runs, and retry the shrunk prefix on failure.
- **`reconstruct`-rejected claimed span is silently swallowed (no `FitReport` entry).** When a heart asserts a span cocircular but `reconstruct`/`Arc::try_new` rejects it (e.g. `sweep.abs() <= ANGLE_EPS_RAD`), the span degrades to per-corner with no `UnblendedJunction`/counter. Per fail-loudly, record an abandoned-span reason in `FitReport` for tuning visibility.
- **`vec3::normalize` has no zero-vector guard.** Divides by `norm` with no check; returns NaN/Inf silently. All current call sites are guarded upstream (radius / `turn_normal`), so no live trigger, but a `debug_assert!(n > 0.0)` belongs here so a future caller traps instead of propagating NaN. (Pre-existing; logic carried from the old `chain.rs`.)
- **`kappa_signal` projects the whole chain's turning onto one plane (`chain_plane` = first turning pair).** `grow_turning_band` re-establishes a per-band plane, so a non-coplanar later band gets a cosine-attenuated κ signal → `grow_kappa_span` under-segments and misses arcs. `in_band_prefix`→`cocircular` prevents wrong geometry (only lost arcs = throughput, never incorrect). `position_greedy` has no such global-plane assumption. - **G2 metric compares |κ| (magnitude), masking signed inflections.** `worst_kappa_jump`/`max_kappa_jump` use `(|κ_prev| − |κ_next|)`, so a +κ→−κ handoff reads as zero jump.
