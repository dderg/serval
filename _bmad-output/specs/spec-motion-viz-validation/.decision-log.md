# Decision log — spec-motion-viz-validation

## 2026-06-25 — create (express mode, interactive)

Distilled from an in-chat brain dump: the user has been manually rendering `viz_pipeline.py` panels to validate motion-planner/fitter behavior and caught real defects that way (on-curve acceleration overshoot under a binding jerk limit; tangent fillets emitted with a raw curvature step, un-eased). Request: turn that manual loop into a repeatable, reviewable regression harness — define G-code + config, assert numeric trajectory metrics (min/max v/a/j, piece counts, total time), and keep the rendered panels as a golden snapshot updated only on explicit human approval. To land before further fitter/planner changes.

**Self-validate verdict.** Pass 1 (coherence): all four capabilities carry intent + success; constraints each rule something out (existing-tooling reuse, acceleration-as-disk-magnitude, determinism, human-approval, land-first ordering); four non-goals fence the scope; success signal names concrete regressions that must turn a case red. Pass 2 (preservation): every load-bearing source claim landed — case definition (CAP-1), the metric list (CAP-2 + `metrics-catalog.md`), human-approved screenshot snapshots (CAP-3), cheap case authoring (CAP-4), the build-on-existing-tooling and accel-matches-viz constraints, and the motivating defects (Why + Success signal). One non-source but load-bearing call was added: the acceleration metric must equal the viz's `√(a_t²+a_n²)` exactly, because that is the quantity the user trusts and used to find the overshoot — logged as a constraint, not silently. No wrapper-only content dropped.

**Adjacency note (not a companion).** `spec-seam-continuity-test-platform` is a sibling harness at a different layer — narrow C0/C1 position-continuity checks at streaming commit seams, in Rust, fuzz-discoverable. This spec is whole-trajectory metric + visual regression from the viz workflow. They are complementary; downstream does not need to read the seam spec to honor this contract, so it is referenced here only, not in `companions:`.

**Open questions carried (need a human decision before build):**
1. Harness home/language — Python pytest around `viz_pipeline`, vs Rust integration test for metrics + Python only for the PNG (likely split).
2. Snapshot mechanism — store-and-human-review (recommended) vs perceptual/pixel-diff threshold.
3. Jerk metric — raw viz jerk has finite-difference seam spikes (unsigned `Arc::kappa` vs signed `Clothoid::kappa`); needs a clean signal or sign `Arc::kappa` first.
4. Case corpus — start with the existing micro-cases, or also real slicer G-code.

**Assumptions:** planner snapshot already exposes all needed fields (confirmed in `viz_pipeline.py`); "pieces" = fitted Line/Arc/Clothoid segments as counted by the `analyze_arc_fit` census.

## 2026-06-25 — update: snapshot-testing model (user correction)

The user corrected the testing model away from hand-authored numeric bounds toward **pure snapshot/characterization testing**, UI-snapshot style: add a G-code case, record the current trajectory output as a checked-in baseline, fail on any later deviation, render before/after PNGs for human comparison, and re-baseline only on explicit approval. The exact v/a/j numbers (spikes included) are recorded, not gated — the planner is deterministic, so they are stable run-to-run and only a *change* trips the test. Language/home is immaterial ("could be just a folder with gcode files").

Resolved three of the four prior open questions: (1) language — immaterial; (2) snapshot mechanism — store-and-fail-on-change, human approve → new baseline; (3) jerk metric — no clean-signal gate needed, the spike is recorded and stable, a change to it is itself a reviewable signal. Reframed CAP-2 from "assert numeric bounds" to "record baseline, fail on deviation," added CAP-4 (capture a freshly-caught bad result as its baseline), and added a non-goal making explicit there are no hand-authored thresholds — the harness is a change detector, not a correctness oracle. Renamed the companion `metrics-catalog.md` → `snapshot-contents.md` (it records, it does not assert). One open question remains: snapshot granularity (full profile vs digest) and the float tolerance that defines a "deviation."

## 2026-06-25 — update: raw trajectory + approval-gated baselines + review UI

User chose to store the **full raw trajectory** (not a digest) as the baseline — to catch any change and to support a richer review UI later (highlight the changed path region, zoom, profile diffs) built on the same artifact, with PNGs as the starting view rather than the baseline itself. New-case baselines are **not** auto-recorded: a newly-added case is pending/red until its first baseline is approved, through the same accept flow as a change to an existing case. Added a review interface as a capability — before/after for every changed or pending snapshot, accept individually or all at once, acceptance writes the new raw snapshots to disk to be committed.

Reframed CAP-2 (raw baseline + new-is-pending), replaced CAP-3 with the review/accept interface, repurposed CAP-4 to the PNG-first-but-raw-enables-richer-views point, and added the store-raw constraint. Resolved the prior "full vs digest + float tolerance" open question (decision: raw), which surfaced its consequence as the new lead open question — raw comparison needs a bit-reproducible or pinned generate/compare environment, else sub-ulp drift false-fails. Second open question: how much review UI lands in v1 (PNG pairs vs the richer web UI). Updated `snapshot-contents.md` to state the result is the full raw trajectory.

## 2026-06-25 — update: per-case planner config (CAP-5)

Added CAP-5: each case fully specifies its planner config — velocity/accel/scv/jerk limits and arc-fit enable + knobs — including mid-case limit changes. These knobs live outside G-code, so the syntax is an open question: a per-folder/per-case `printer.cfg` (matches the viz `-c` flag and Klipper's config model), in-G-code commands (`M204`/`SET_VELOCITY_LIMIT` plus a custom arc-fit toggle), or a sidecar — and the two can combine (base `printer.cfg` + in-line overrides). Two cases with identical G-code but different config must produce different baselines. The float-drift reproducibility question is explicitly deferred ("once we get to it") per the user.
