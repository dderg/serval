# Decision log — spec-single-mcu-piece-frame

## 2026-06-23 — create (distilled from conversation: dense-stream delivery investigation → wire-protocol fix)

Input was a conversational design session, not a file: a multi-step bench
investigation (Neptune `PieceStartInPast` crashes) that localized the root cause
to single-axis wire framing and converged on a single-MCU (multi-axis) `PushPieces`
frame. No source file to absorb — `sources: []`.

**Pass 1 (coherence).** All three capabilities carry intent + success. Intents
state WHAT (deliver one MCU's axes per transaction; carry multi-axis blocks; fail
loud on corrupt/oversized/mismatched frames); the byte-level HOW lives in the
`wire-format.md` companion, satisfying rule 2. Constraints each bend design — the
256 B buffer caps batching, the clean break forces a version-byte bump and
lockstep flash, the framing-only rule forbids touching the FFI seam. Six non-goals
fence the scope (deep batching, pipelining, empty-piece skip, horizon/ring tuning,
EtherCAT cosmetic bug, FFI/ring/PieceEntry changes). Success signal is demonstrable
against a real bench run (same G-code prints through; one round-trip per MCU;
0.47×→≥1×). No coherence fixes required beyond normal distillation.

**Pass 2 (preservation).** Every load-bearing claim landed: the single-axis→single-
MCU framing, the round-trip arithmetic (3×~5 ms = 15 ms, 0.47×), the diagnostic
that ruled out ring/horizon (`piece_count=1`, `room` 61–261), the fault identity
(`65228`, `print-1782209653`, layer 3), the 256 B frame budget and ~2 pieces/axis
ceiling, the C/Rust boundary preservation (FFI and rings unchanged), the clean
break + version bump + flash-both rule, fail-loud bounds/static assert, and
idempotent retry. The before/after byte layouts and the file-by-file change surface
went to `wire-format.md`. Two items were deliberately surfaced as open rather than
asserted: the wire layout was still under review (not greenlit) when distilled, and
whether to also grow `MCU_TX_BUF_SIZE` for deeper batching. Wrapper-only content
dropped: the conversational scaffolding and the "shall I start step 1?" prompts —
process ceremony, no downstream value.

**Verdict.** Coherent and preservation-complete. Two open questions gate the
firmware step (ratify the wire layout + version bump; decide on the buffer-size
question). Until those are answered the host-side protocol work (CAP-2 unit tests)
can proceed, but the C `piece_sink` change should wait.

## 2026-06-23 — update (party-mode roundtable + frame-level response decision)

A four-expert roundtable (architect, dev, test-architect, PM via bmad-party-mode)
pressure-tested the spec. All four returned **greenlight-with-conditions**; nobody
no-go. Convergent conditions, now folded into CAP-2/CAP-3 and `wire-format.md`:
host all-or-nothing via a single `all_ok` gate; `runtime_write_piece` confirmed
full-slot-overwrite; CRC verified before the parse loop; bounds-checked
`axis_count`/`axis_idx`/`piece_count` + duplicate rejection + static assert; ASan
fuzz of the C parser before any hardware; version byte must *refuse* a mismatch;
`arrival_clock` sampled at frame-receive-complete; and a green bench trace on the
original crashing G-code as the real greenlight.

**Decision — response is frame-level, not per-axis.** Prompted by the user's
question "should the MCU even be able to say OK if it's not for everything?", we
collapsed `PushPiecesResponse.result` from per-axis to one frame-level verdict. The
only per-axis "not OK" the runtime produces in normal operation is ring overflow
(`Overcommit`/`RUNTIME_ERR_RING_FULL`) — a host pacing/desync bug, not a per-axis
recover; every other not-OK is frame-global or a config bug. On a hard-real-time
path there is no legitimate partial-success (axis 0 OK / axis 1 not = desync =
wrong motion). This **designs out** the partial-commit-then-retry hazard that the
dev and test-architect both ranked the #1 risk: a mid-frame commit failure
fail-loud halts the whole engine (no retry), so half-committed rings never execute;
only pre-commit transport failures (CRC-gated) are retryable, and those are
zero-committed. This closes Murat's "frame-level ACK vs per-axis result" open
thread. `front_start_time` stays per-axis as a diagnostic-only echo.

**Resolved:** the wire-layout ratification open question (request shape ratified by
the roundtable; response shape decided here). The version-refuse-on-mismatch is now
in CAP-3.

## 2026-06-23 — clarification: chip-agnostic, not F401-specific

User flagged that the spec was leaking the Neptune bench's chip (F401) into the
design. Corrected: the protocol change is chip-independent — any MCU with multiple
axes on one transport benefits. `MCU_TX_BUF_SIZE` is a shared `#define` (256)
compiled into every chip's firmware, sized for the fleet's most RAM-constrained MCU
(today the F401); the host caps pieces to it for every MCU, never hardcoding a chip,
and could move to per-MCU capability negotiation later. The C `piece_sink` change is
one file built for all targets, so it lands on all MCUs at once. F401/Neptune remain
as the concrete *reproduction*, not the design basis.

## 2026-06-23 — pre-bench gate: parser extracted + host-verified (61067a3a9)

The C `piece_sink` was extracted into its own TU (`src/piece_sink.c`) behind a
~6-symbol seam and is now host-compiled + verified by `rust/piece-sink-harness`:
behavioural invariants, a differential round-trip against the Rust codec (host
encoder → C parser → host decoder agree byte-for-byte), and a byte-stream fuzz —
9/9 green, clippy clean. `scripts/fuzz-piece-sink.sh` runs the same parser under
AddressSanitizer/UBSan over 2M random frames — clean. This compile-verifies the
previously-blind C and proves the parser memory-safe on arbitrary input, closing
Murat's Tier-1 gate. Remaining before bench: MCU firmware build (whole-image
compile-check) + lockstep flash + the green trace on the original crashing G-code.

## 2026-06-23 — decision: collapse-only, F401 buffer untouched

User chose **round-trip-collapse only** and to leave `MCU_TX_BUF_SIZE` (256 B) as
is — F401 SRAM (64 KB) sizes that buffer under real pressure, and the principle is
one change at a time. Winston's "pay the lockstep coupon twice" argument was
defused by noting the buffer raise is a later MCU-side constant bump + host cap, not
a second protocol/version break — so deferring is cheap. No open questions remain;
Non-goals already fence deeper batching as a separate effort. Host-side protocol
work (CAP-2: `messages.rs` types + round-trip tests) is cleared to start; the C
`piece_sink` change follows, gated by the CAP-3 conditions and a green bench trace.
