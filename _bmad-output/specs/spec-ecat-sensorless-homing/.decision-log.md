# Decision Log — spec-ecat-sensorless-homing

## 2026-06-26 — Create

**Inputs.** User intent (add EtherCAT sensorless homing; support AWD, CoreXY, cartesian; prefer MCU-only; weigh built-in drive homing vs. our own; idea of keeping host drip and arming a trigger that fires a function instead of faulting on missed track) + the A6-EC servo manual PDF (279 pp) + a codebase exploration of this fork.

**Mode.** Interactive, express distill (input was rich — both the manual and substantial existing scaffolding grounded the kernel; no elicitation needed).

**Key findings driving the spec.**
- The EtherCAT/servo path, CSP drip, homing-limit messages (`SetDriveLimits`/`RestoreDriveLimits`/`SeedServoHome`), `homing_following_error`/`homing_max_torque` config, op-mode switching (`seed_home.rs`), and `ec_rt_get_following_error` already exist on the base branch. The feature is a keystone, not greenfield.
- The single missing piece (the "trigger"): nothing in the `ethercat-rt` DC loop converts an armed missed-track (following error past threshold) into an `EndstopTrip`. That maps exactly onto the user's described idea.
- Manual confirms the user's mental model is sound: CSP exposes `60F4h`/`6077h`/`606Ch`; `6065h` is the deviation fault window (raise it to avoid Er47.0); methods −1/−2 are the drive's own sensorless hard-stop homing.
- Option A (drive-autonomous HM) rejected as the coordinated mechanism because it cannot coordinate the two coupled motors of CoreXY/AWD; Option B (host drip + RT-edge trigger) chosen and is uniform across all three kinematics.
- "MCU only" reconciled: the drives are not behind the H7/F446 step/dir MCUs; the `ethercat-rt` RT endpoint is the MCU-equivalent edge, and that is where the trigger lives. Recorded as an assumption.

**Pass 1 — Coherence.** 5 capabilities, each with intent + success (rule 1). Intents are WHAT (home sensorlessly, arm/disarm, detect-and-trip, work across kinematics, latch frame); HOW lives in design.md/drive-reference.md (rule 2). Constraints each rule something out — no autonomous HM, no fault during arm, mandatory restore, torque cap, fail-loud, edge placement, reuse-not-reinvent (rule 3). Non-goals explicit, 5 of them (rule 4). Success signal is a concrete demonstrable machine behavior (rule 5). IDs CAP-1..5 fresh (rule 6). Prose kept lean (rule 8). Six genuine open questions logged rather than invented-answered.

**Pass 2 — Preservation.** User claims all landed: AWD/CoreXY/cartesian → CAP-4 + design.md coordination section; MCU-only preference → assumption + edge-placement constraint; built-in-vs-own analysis → design.md Options A/B; "keep host drip + arm trigger + fire function not crash" → CAP-2/CAP-3 + lifecycle. Manual load-bearing content (modes, OD objects, methods −1/−2/35, Er47.x, DI signals) → drive-reference.md with page cites. Wrapper-only content dropped: none of substance (the BMad ceremony framing itself).

**Verdict.** Coherent and preservation-complete. The spec's honest core: this is a keystone over largely-built scaffolding, the one real gap is the armed missed-track→`EndstopTrip` trigger in the RT edge, and the chief unknowns are the trigger discriminator, `endstop_id` allocation for switch-less servo axes, and coupled-axis trip-clock skew. These are surfaced as Open Questions, not silently resolved.

## 2026-06-26 — Update (user review of open questions)

User reviewed the six open questions and the design. Decisions folded in:
- **Current state corrected.** The CSP drip today triggers off a *separate MCU's* endstop, not the drive. Captured in Why and design.md; the feature replaces that trigger source with the drive itself.
- **Architecture steer — servo as a host-side virtual endstop, like a probe.** Resolves the former `endstop_id` open question: reuse `allocate_provider_id` / `arm_remote_trigger` (the probe/`RemoteMotionEndstop` path), arming against the `ethercat_node` engine. New design.md section "The servo as a virtual endstop"; CAP-3 reframed; gap-inventory updated.
- **Q3 (built-in HM single-motor fallback) dropped.** User saw no point; HM is now excluded outright (Non-goal hardened, design.md Option A rejection made flat).
- **Q4 (gantry/bed squaring) dropped** as irrelevant to the task — removed from Non-goals and Open Questions.
- **Q5 (fine re-home) resolved** — left to the user via the existing `use_sensorless_homing` flag; now a Constraint, not a question.
- **Q6 (coupled trip-clock skew) resolved** — coupled drives share one EtherCAT DC loop, so the first detector stops all motion on one DC timebase; now a Constraint/Assumption, not a question.
- **New nuance — AWD freewheel.** User raised possibly freewheeling one motor of a coupled AWD pair ("let's see if it's necessary"). Kept as the one remaining design Open Question; default is symmetric low-torque homing of both.
- **Trigger discriminator (was Q1) retained**, reframed around the user's "reliable yet not violent / easy to tune" framing.

Open questions now: (1) trigger discriminator/tuning, (2) AWD freewheel necessity. Both are empirical/bench-settled; neither blocks starting the keystone trigger work. Spec remains coherent and preservation-complete after the edits.

## 2026-06-26 — Update (trigger brainstorm → torque trip + local stop)

Brainstormed open-question #1 (the "violence" of pin homing). Decomposed into four orthogonal knobs: what to trigger on, approach mode, stop locality, multi-touch. Root cause named: CSP commands an unreachable position so the loop winds torque to the cap and holds it (peak force) until the trip propagates (press duration).

Decisions folded in:
- **Trigger on actual torque (`6077h`), staying in CSP.** Torque sets contact force directly; position-deviation distance is inherently violent. Keeps planner-owned kinematics (CoreXY/AWD free). CSV→CST documented as fallbacks with their CoreXY-coordination cost. CAP-3 reframed; new design.md section "Trigger design"; drive-reference already lists 6077h.
- **Local in-cycle stop in `ethercat-rt`**, mirroring the regular MCU's existing endstop local-stop (user confirmed that mechanism already exists "so we do it the same way"). Bounds press-duration to ~one DC cycle. New Constraint; lifecycle diagram + gap inventory + build sketch updated.
- **Gentleness promoted to a hard requirement** (two bounds: torque cap on peak force, local stop on duration) — user made clear it is load-bearing, not a nicety.
- **New enabling dependency surfaced by the user:** the homing drip isn't accelerated smoothly, so the start-of-move transient false-trips a lowered torque threshold. Jerk-limited homing-drip ramp in `home_drip` is a prerequisite for a gentle threshold and also improves regular pin homing. Captured as Open Question #1 (sequenced ahead of threshold tuning) and a gap-inventory row; explicitly separate scope but quality-gating.

Open questions after this round: (1) smooth homing-drip acceleration (enabling, separate), (2) residual torque-threshold tuning, (3) AWD freewheel necessity.
